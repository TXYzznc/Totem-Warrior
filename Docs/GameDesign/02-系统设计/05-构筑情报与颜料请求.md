# 构筑情报与颜料请求

> 状态：数据与交互规则已确认并实现；信息密度待 UI 和试玩验证

## 系统目的

构筑情报为 PVP 反制提供可信输入，颜料请求让双人队能够在不自动共享库存的前提下进行资源协作。二者共同把构筑从个人菜单变成对局层策略。

## 快照时机

每次进入构筑阶段时按固定顺序处理：

1. 战斗阶段结束。
2. 所有仍处于倒地状态的玩家立即淘汰。
3. 系统读取 6 名参赛者当前构筑、属性、状态和从开局累计的成果。
4. 生成该构筑阶段的冻结快照。
5. 构筑界面打开。
6. 玩家本阶段修改不会实时更新其他人的快照。
7. 下一次构筑开始时才公开新的边界状态。

## 为什么冻结而不是实时更新

实时公开会导致玩家互相等待和无限镜像换装，最后一秒修改成为最优策略。冻结快照让玩家只能依据已发生的事实预测下一步，并给每个人保留一次不公开的调整机会。

## 当前构筑快照

每名参赛者显示：

- 当前存活、倒地结算后淘汰或已撤离状态。
- 已装备的身体部位。
- 临时图案编号 P01/P02。
- 火、冰或雷元素。
- 配置中的无精确数值效果文本。
- 当前属性。
- 基础属性和局内强化加成分开显示，并使用不同文字颜色。

不显示纹身的内部倍率、概率和冷却数值。

## 本局个人成果

当前纯 PVP 版本从开局累计显示：

| 类别 | 精确数据 |
|---|---|
| 对抗输出 | 对玩家伤害、击倒、淘汰 |
| 队伍生存 | 治疗队友、提供护盾或减伤、成功救援 |
| 功能贡献 | 净化或解除控制、有效控制时长/次数、为队友创造的增伤收益 |
| 资源贡献 | 资源获取、资源分享 |
| 风险表现 | 自身被击倒次数 |

这些数据展示整局累计值，不是只显示上一轮。

原讨论曾包含 PVE 伤害与 PVE 击杀；由于当前 First Playable 已明确为纯 PVP，这两个字段不进入活动 UI、统计和配置。未来 PVE 正式回归后再重新加入。

## 信息层级建议

六人信息不应同时以相同权重铺满屏幕。建议层级：

1. 默认显示队伍、存活状态、主要纹身方向和关键成果摘要。
2. 选择某玩家后展开六部位、属性拆分和完整成果。
3. 自己与队友保持快捷切换，对手按队伍分组。
4. 高威胁、频繁倒地或明显领先只能用辅助标记，不替玩家自动下结论。

最终排版和视觉仍属于 UI 美术设计，但信息字段和快照时序属于玩法合同。

## 颜料请求流程

```text
玩家选择请求资源
→ 选择火/冰/雷
→ 输入请求数量
→ 最大值取队友当前拥有量
→ 向唯一队友发送请求
→ 队友同意或拒绝
→ 同意时再次校验实际库存
→ 原子扣除队友库存并增加请求者库存
```

## 请求异常规则

- 发起时数量不能超过队友当时库存。
- 批准时必须再次校验，因为队友可能已经消费颜料。
- 批准时库存不足，事务整体失败并提示库存已变化。
- 拒绝不改变双方库存。
- 请求过期不改变双方库存。
- 阶段结束时未完成请求安全失效。
- 不能向敌队或自己发送请求。
- 转移是颜料所有权变更，不是共享库存引用。

## 设计意图

自动共享会抹平队伍内的资源决策，也可能让一名玩家无意中消耗另一人的计划。显式请求保留个人所有权，同时允许队友根据构筑方向主动协商。

## 试玩观察项

- 玩家能否在 45 秒内阅读信息并完成构筑。
- 精确成果是否导致玩家只针对领先者。
- 无数值纹身文本是否足以形成正确判断。
- 资源请求是否常被使用，还是操作成本高于价值。
- 队友是否愿意分享颜料，还是个人构筑永远优先。
