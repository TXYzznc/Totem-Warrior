# 开发执行约束

> 生效日期：2026-08-13  
> 适用范围：当前 First Playable 的清理、重建、集成与玩法验证

## 唯一信息源与职责边界

- `Docs/GameDesign/` 是玩法、规则、数值、版本边界和玩家体验的唯一标准信息源。
- `第一版开发任务表.xlsx` 是任务顺序、依赖、里程碑、工时区间和状态的用户维护来源。
- OpenSpec 负责一组相关开发任务的需求变化、技术方案、可测试场景与实现任务分解。
- 代码、数据、资源和测试只负责实现与验证，不得反向改写已确认策划。
- 旧 OpenSpec、旧代码、旧数据表和旧测试只能作为历史证据；与 `Docs/GameDesign/` 冲突时必须服从当前策划。

## 第一版开发任务表所有权

- 本次初始任务表由 AI 按已确认范围创建并完成结构、公式、依赖和视觉验收。
- 初始创建验收后，任务表只允许用户本人维护。
- AI、Agent、SKILL、脚本和自动化工具不得编辑、覆盖、另存后替换或重算后回写该工作簿。
- AI 可以只读分析任务表，并向用户报告建议状态、实际工时、依赖变化和拆分建议；是否写入由用户决定。
- 禁止创建并行权威副本。临时导出、截图或分析文件不得冒充开发台账。

## 现状继承规则

本项目不是从零开始，但旧业务不能视为可靠基线：

- GF_X 框架、Unity 工程基础、Launch 启动链和通用诊断能力优先保留并复验。
- `Assets/Game` 中现存美术资产均已确认并完成导入，必须按“保留资产”处理；只验证运行时接口和策划覆盖，不重新判断其美术是否通过。
- 正式角色模型、Prefab 和动画当前不存在，必须标记为“尚未制作”，不得保留指向不存在资产的完成状态或资源键。
- `Assets/Game/Sprites/UI/FirstPlayable/` 中现存 UI 资源全部保留；只补充策划需要但当前目录中不存在的页面、组件和状态。
- `Assets/Game/Scripts/` 中现有业务运行时、业务数据模型和业务 UI 只作为迁移参考，不默认继承其结构。
- 现有业务 DataTable、Gameplay Catalog、Runtime Asset Catalog 必须按新策划重新定义；不得在旧字段上继续堆兼容层。
- 旧测试只保存有价值的场景、夹具和诊断方式。若断言的是旧规则，应替换而不是强行维持通过。

## 重建与清理顺序

采用“新骨架先行、分域切换、零引用后删除”：

1. 先登记保留资产、旧业务边界、序列化引用和回滚证据。
2. 为当前阶段建立新合同、新配置和自动化测试。
3. 将调用方切换到新入口，并完成编译、EditMode、PlayMode 和诊断验证。
4. 确认代码、Prefab、场景、配置、测试和资源目录均无旧引用。
5. 最后删除对应旧脚本、旧表、旧枚举、旧资源键和旧诊断。

禁止先批量删除业务目录再修编译；禁止为了保住旧实现而向新设计添加兼容规则。

## 任务拆分和估算

- 程序投入按个人开发每周约 20 小时折算；美术资源制作单独统计。
- 工时是区间估算，不是日历承诺。
- 单项任务最高估算不得超过 18 小时；超过时必须在开始前拆分。
- “并行组”表示依赖上可独立推进，不表示单个开发者必须同时开工。
- 低置信度任务在进入 OpenSpec 前重新检查范围和估算。
- P0 是里程碑必需项；P1 只能在不破坏 First Playable 验收门时后置。

## OpenSpec 分组和命名

- 一个 OpenSpec 原则上覆盖 2～5 个目标一致、依赖连续、能共同验收的任务。
- 不得跨越阶段验收门，也不得把整张任务表一次性放进一个 change。
- change ID 使用小写英文、数字和连字符组成的 `kebab-case`。
- 非并行命名：`<两位批次>-<任务编号组合>-<英文概要>`。
- 并行命名：`<两位批次>-parallel-<领域>-<任务编号组合>-<英文概要>`。
- proposal、design、specs 和 tasks 必须列出任务表中的完整原始任务 ID。
- 建立 OpenSpec 前必须从 `Docs/GameDesign/` 核对对应权威规则；发现空缺时先回到设计讨论。

## 状态与完成规则

- 初始业务重建、业务数据和清理任务统一为“未开始”。
- 明确保留的框架或美术资产可以标记为“待复验”，但不得自动算作已完成。
- 发现旧实现与新规则冲突时使用“待返工”。
- 单项任务达到 DoD 后进入“待验收”，不得由执行该任务的 AI 自行标记“已完成”。
- 阶段验收门通过并由用户确认后，才开放下一阶段关键路径。
- 任务状态建议值：未开始、进行中、受阻、待复验、待返工、待验收、已完成、已取消。

## 美术并行和接入

- 场景与交互物品制作已基本完成，当前路线以保留资产审计、接口复验和主工程接入为主。
- UI 已确认资源集中在 `Assets/Game/Sprites/UI/FirstPlayable/`；需对照主菜单、HUD、构筑、情报、资源请求、倒地/观战和结果信息架构做覆盖审计，目录中不存在的部分才进入制作计划。
- 程序灰盒不等待 UI 正式资源；但 First Playable 最终验收必须等待本版本所需 UI、纹身和战斗反馈资源完成接入。
- 正式美术只能替换视觉子对象、材质、贴图、动画和表现层，不得改变逻辑根、碰撞、锚点、事件名和运行时数据合同。
- 已完成资产不能倒逼玩法修改；若运行时接线或页面覆盖与策划不一致，应修正接线或补缺口，不得把 `Assets/Game` 中现存美术重新标记为未确认。

## 测试和交付边界

- 任务表中的 DoD 是进度门，不替代正式测试用例。
- 每个 OpenSpec 在实现前按最新规格建立或更新 EditMode、PlayMode 和人工验收场景。
- 阶段门至少检查：编译、缺失引用、旧入口零引用、配置合法性、确定性结果、PlayMode smoke、GF_X 全量诊断。
- 全量诊断自动入口使用项目规定的 `totem_diagnostics_run_all`；不得用通用菜单执行接口代替。
- First Playable 完成需要同时满足结构闭环和人工玩法验证，不能只凭自动测试宣称玩法成立。
