## GameDesign 的权威职责

- 解释为什么选择 6 人、单枪械、五轮和边界快照。
- 描述玩家目标、对局动态、风险和体验。
- 标明当前、后续、暂缓和取消内容。
- 保存尚未进入实现的长期 PvPvE 方向。
- 作为项目开发中玩法、数值、术语、范围与验收意图的唯一标准信息源。

## OpenSpec 职责

- 使用 MUST/SHALL 定义精确运行合同。
- 给出 WHEN/THEN 场景、异常规则和验收条件。
- 建立 change、tasks、baseline 和 evidence。
- 在实现完成后合并主规格并归档历史。
- 只能实现 GameDesign 已确认的结论；不能把代码现状或临时测试行为提升为策划规则。

## 配置职责

配置表负责具体可调数据，例如：

- `ZoneShrinkConfig` 的缩圈半径、时间和伤害。
- `WeaponConfig` 的当前步枪数值。
- 图案和公开效果文本。
- 元素、反应和表现延迟。
- `MapResourcePickupConfig` 的数量区间、权重和轮次。
- 撤离点生成数量。

配置是策划规则的实例，不应偷偷扩大版本范围。例如在表中增加 P03 记录并不能绕过 First Playable 只允许 P01/P02 的版本规则。

## 变更流程

1. 在 GameDesign 中确认玩家问题、规则、数值与版本归属；存在疑问时先与项目负责人讨论，不自行猜测。
2. 更新决策记录、名词表、状态总表和开放问题。
3. 对跨模块或大型改动建立新的 OpenSpec change。
4. 将规则拆成可验证 Requirement 与 Scenario。
5. 实现、测试、诊断并保存证据。
6. 验证通过后合并主规格与归档 change。
7. 回写 GameDesign 的实现与验证状态。

## 不应直接作为新需求来源

- 已清理的旧代码和旧配置。
- Git 历史里的旧 Enemy/PVE/Boss 方案。
- 占位 UI 或 fallback 美术的外观。
- 自动测试为了加速流程使用的测试输入。
- 文件名对无正式名称图案的临时描述。
