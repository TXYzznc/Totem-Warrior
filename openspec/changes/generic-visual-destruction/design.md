## Context

项目使用 Unity 2022.3 的 URP，现有小型可交互道具若采用预制碎块替换，会为每个模型带来额外的破损网格、Collider、Rigidbody 和特效配置成本。`Assets/DestroyIt` 已证明该路线适合高保真残骸，但不满足“挂载组件即可使用、无专属破碎美术、性能优先”的目标。

首期服务对象为具有一个或多个不透明静态 Renderer 的小型场景道具，例如陶罐、木箱、石块与金属杂物。攻击、交互和对象销毁逻辑负责决定何时触发；本能力只接收世界空间命中位置和可选强度，不读取输入，也不承担耐久度或掉落物业务。

## Goals / Non-Goals

**Goals:**

- 通过单个可配置组件让普通小型静态道具获得短暂、可读的破坏视觉。
- 使用共享 Shader、噪声、碎屑 Mesh 与粒子材质，不要求每个道具提供破损网格、碎片 Prefab 或专属裂纹贴图。
- 以受击位置为中心提供裁切崩解、短暂顶点外移和材质类别化碎屑/粉尘的组合效果。
- 让同屏效果数量具有明确上限，并在预算耗尽时保留低成本 Shader 或直接隐藏的降级路径。
- 通过 MaterialPropertyBlock 写入每实例参数，避免复制材质；VFX 走项目既有 `TotemVfxService` / 资源目录与对象池约定。

**Non-Goals:**

- 运行时真实网格切割、碎片 Collider、持久物理残骸、NavMesh 更新或建筑结构模拟。
- 对 Skinned Mesh、透明/折射材质、多层复杂 Shader、Terrain 与大型建筑提供首期支持。
- 自动判断物体的真实材质；道具作者必须选择有限的破坏材质类别。
- 改造或依赖 `Assets/DestroyIt` 的预制碎块系统。

## Decisions

### 1. 采用“Shader 母体崩解 + 共享 VFX”而非运行时碎裂

组件在效果期间驱动原模型的 URP 崩解 Shader：对象空间噪声和受击球形距离场决定可见区域、裁切边缘及爆散进度；顶点沿由受击点导出的方向做短时、受限位移。碎屑与粉尘由共享 VFX 补足真实感，原模型结束后隐藏或交给调用者回收。

该方案不试图把连续三角网格变为真实独立碎块。噪声位移单独使用会呈现果冻式膨胀，裁切单独使用会像溶解；二者加上粒子可在极低资产成本下形成“脆性崩解”的视觉错觉。

替代方案：

- 预制碎块替换：视觉最真实，但要求每个道具制作破损版本且有物理开销，因此不采用。
- GPU/CPU 实时切割：可对应命中位置产生真实断口，但复杂度、内存与最坏帧成本不符合首期目标，因此不采用。
- 仅播粒子后隐藏：性能最佳但缺少母体破坏过程，仅作为最低档降级。

### 2. 使用对象空间共享噪声与 MaterialPropertyBlock

噪声采样基于对象空间位置与实例随机种子，可在不同模型上复用同一张平铺噪声纹理，避免要求 UV 专用贴图。组件在初始化时缓存 Renderer 和 MaterialPropertyBlock；播放时只写入破坏中心、时间进度、随机种子和材质类别参数，不实例化 Material，也不在 Update 中产生 GC 分配。

受击点从世界空间转换为每个 Renderer 的对象空间。若一个对象有多个 Renderer，它们使用同一场次随机种子和世界命中点，以保证崩解节奏一致。

替代方案：为每个模型烘焙破坏遮罩或顶点色。其局部裂纹控制更精确，但违背零专属破坏资产目标，因此仅保留为未来高级扩展，不作为首期依赖。

### 3. 保留原有 PBR 光照，边缘使用受控视觉增强

完整模型在崩解前段保持原材质的 URP 光照与釉面/粗糙度响应，以避免从 Lit 突变为 Unlit。破坏边缘允许短暂使用颜色、Emission 或抖动裁切增强可读性；不关闭整件物体的光照模拟。

替代方案：全程 Unlit 爆散。实现简单，但会使釉面陶罐等资产出现明显的光照跳变，不采用。

### 4. 以显式材质类别选择共享 VFX，并设计三档预算

组件暴露有限枚举：陶瓷、木材、石材、金属。类别选择对应共享的碎屑 Mesh、颜色、粉尘和位移强度，不自动分析材质。全局视觉破坏服务维护活跃效果令牌：

- 完整档：Shader 崩解 + 少量碎屑 + 粉尘；
- 简化档：Shader 崩解 + 粉尘或极少碎屑；
- 预算耗尽：快速裁切/隐藏，不生成 VFX。

令牌按效果寿命归还；碎屑和粒子必须使用可复用对象或项目 VFX 服务，禁止每次破坏创建独立资源和 Rigidbody。

替代方案：每个组件独立计算同屏数量。它无法可靠控制全局最坏情况，因此不采用。

### 5. 生命周期由调用方拥有，组件只保证一次播放

组件提供显式的破坏视觉入口，接受命中点、强度与完成回调/事件。第一次播放后进入终态，忽略重复触发；结束后由配置决定隐藏 Renderer、禁用 GameObject，或通知上层进行既有对象池回收。组件不直接销毁 GameObject，避免与掉落物、任务、网络同步或对象池生命周期耦合。

## Risks / Trade-offs

- [低顶点模型的顶点爆散不明显] → 保证裁切和边缘效果独立可读；对低顶点模型自动降低位移依赖，并由粒子承担飞散感。
- [复杂/不支持的 Shader 无法注入崩解参数] → 首期仅验证指定 URP 不透明材质；检测失败时直接走粒子/隐藏降级，并在 Inspector 显示警告。
- [透明粒子造成过度绘制] → 限制发射数量、寿命和屏幕并发；粉尘优先使用低分辨率纹理、软边裁切与对象池。
- [大量同时触发导致 GPU 峰值] → 全局令牌控制、三档降级、固定最大持续时长，并在目标设备用 Profiler 验收。
- [共享碎屑与特定模型外观不完全一致] → 将其明确定位为材质级视觉提示；陶瓷保留浅色陶土和少量釉面色变体以提高辨识度。
- [多 Renderer 对象出现不同步] → 每次播放为同一对象生成统一场次数据，并向缓存的全部 Renderer 写入同一进度。

## Migration Plan

1. 建立共享 Shader、VFX 和运行时组件，但不修改任何现有道具或 `DestroyIt` 内容。
2. 用 `INT-PROP-009` 陶制储罐作为首个验证道具，保留其原始模型与材质作为回滚基线。
3. 在独立测试场景验证完整档、简化档、预算耗尽档以及重复触发和对象池回收。
4. 通过目标设备 Profiling 后，按材质类别逐步为现有小型道具添加组件。
5. 回滚时移除组件或关闭全局服务；原始 Renderer、材质和玩法逻辑无需恢复或迁移。

## Open Questions

- 首期目标平台与最坏情况下的同屏破坏次数尚未量化；任务阶段需把它们转为具体 GPU/CPU 帧预算与并发阈值。
- 现有 `TotemVfxService` 是否已支持同步、非 Addressables 的场景 VFX 实例化和回收，需在实现前确认；若不支持，应仅扩展该服务而不引入平行对象池。
- 破坏完成后的最终对象生命周期由互动道具系统、掉落系统还是场景对象池管理，需在接入首个业务对象前确定。
