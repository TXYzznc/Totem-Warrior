## Context

现有目录已定义绿洲新城的统一尺度、24 种建筑类型、32 类装饰、可进入建筑配额和生产流水线。BF-01 是已完成 P2/P3 的先导资产，BF-02 已具备 P0/P1 文档；BF-03～BF-24 缺少统一的 P0 与 P1 输入。利益相关方为玩法/关卡设计、3D 美术、Unity 白模执行及负责确认 P0/P1 的用户。

本次交付仅为白模前置准备。后续制作真实 Unity 白模时，必须用多色方块清晰区分结构、房间功能、通行、垂直交通与交互净空；任何建筑必须拥有可进入、可返回且可探索的内部。

## Goals / Non-Goals

**Goals:**

- 为 BF-03～BF-24 的每个建筑类型创建一张可集中确认的 P0 功能任务卡。
- P0 获确认后，为每个类型生成同一套 P1 白模前置文件：详细设计案、布局 JSON、视觉提示词和白模制作规范。
- 使 P1 明确可探索室内、楼层、楼梯、出口、通行宽度、交互净空、局部坐标、接街关系及多色白模语义。
- 允许后续将一个已确认类型原型安全地实例化到 65 座实际建筑，而不在本阶段编造城市坐标。

**Non-Goals:**

- 除用户已确认的 BF-02～BF-05 P1 商店差异化文档外，不修改既有建筑；不创建 `.unity` 场景、ProBuilder 对象、截图、FBX、贴图、碰撞网格或运行时代码。
- 不制作最终城市俯视布局、实例地块坐标、道路/地形、Boss/事件配置或正式效果图。
- 不把效果图、提示词或美术判断提升为尺寸真源。

## Decisions

### 以建筑类型而非实例作为 P0/P1 的确认单位

BF-03～BF-24 共 22 个类型、65 个后续实例。P0/P1 按类型建立，以实例配额、变体边界和接街关系约束后续复制；不为每个住宅先创建重复文件。替代方案是按 65 个实例分别建档，但会在无最终地图坐标时产生虚构约束并显著提高确认成本。

### P0 是唯一的功能确认门

所有 P0 文件按功能组并行起草，但在用户集中确认前不生成任一类型的 P1。P0 必须包含：身份/层级限制、最小可探索空间、进出与垂直流线、玩法锚点类别、禁止绑定功能和验收条件。替代方案是直接补 P1，但会把未确认的功能决策固化为尺寸和楼梯。

### P1 使用文件组而不是单一说明文档

每个 P1 包含 `详细设计案.md`、`楼层布局.json`、`设计图需求提示词.md` 和 `白模制作规范.md`。详细案与 JSON 共同为尺寸/位置真源；提示词仅作视觉参考；白模规范明确多色方块、Collection/对象命名、碰撞与验收。替代方案是只提供一份文字文档，但无法可靠驱动 Unity/Blender 和结构 QA。

### 白模色彩是语义分类，不是美术定稿

后续 P2 必须至少使用：结构外壳、可走地面、功能房间、垂直交通、门洞/出口、交互净空、危险/维护禁区七类颜色，且颜色在全体建筑内一致。颜色仅服务结构阅读，最终模型不可继承为材质。替代方案是统一灰模，但无法快速辨识内部连通与楼梯职责。

### 使用本地原型坐标和接街合同

每个类型原点设于首层完成面中心，正门面向 `-Y`，并记录建议分区、街道类型与外部净空。最终地图锁定后才将局部坐标转换为实例世界坐标。替代方案是预填世界坐标，但会与后续地图布局冲突。

### 四座随机商人店采用不同的体量与平面原型

BF-02～BF-05 全部保持低地标、单层且可探索，但不得复用“矩形前店＋后部双房”的同一结构。BF-02 固定为 12×16m 紧凑颜料调制店；BF-03 为 14×12m 横向补给站和双跨遮阳门廊；BF-04 为约 14×14m、围绕半室外检视小院的 L 形旧件院店；BF-05 为 10×15m、入口退入织物屏风门廊的窄长廊店。

这种方式以水平体量、入口构图、室内流线和半室外空间建立差异，而非为小商店添加不必要的二层或塔楼。替代方案是仅改招牌与陈列，但无法在白模五视图和可探索平面中清晰辨识四种功能。

## Risks / Trade-offs

- [22 张 P0 同时输出导致术语或流线不一致] → 使用统一 P0 模板、按公共/生产/住宅/特殊设施分组，并在合并前做跨卡 QA。
- [住宅类的多实例复制导致单调] → P1 定义尺寸和入口/楼梯/庭院的允许变体范围；实例化时遵守配额和本地道路条件。
- [高差或楼梯在白模时被忽略] → 每个多层类型必须在 P0 明示垂直交通，在 P1 使用可计算的踏步/平台/净高数据，并纳入 JSON 验收字段。
- [颜色方块被误解为最终美术] → 每个 P1 声明色彩仅为 P2 结构可读性合同，正式建模另遵循城市材质规范。
- [P1 在未确认 P0 前被提前创建] → 任务顺序硬性阻塞，目录中只允许出现 P0 草案直到用户给出集中确认。
- [四家商店因统一模块而再次趋同] → 将体量、入口构图、房间拓扑和外部阈值写入详细设计案、JSON、提示词及白模规范，并用五视图白模验收。

## Migration Plan

1. 生成并审校 BF-03～BF-24 的 P0 草案，统一交给用户确认。
2. 用户确认后按四个建筑组并行生成 P1 文件组，并为每组执行 JSON/尺寸/流线检查。
3. 汇总白模执行索引，交接给后续 Unity ProBuilder 制作；真实白模场景不属于本变更。
4. 若用户驳回任一 P0，仅修改该类型 P0 并保持其 P1 阻塞；不回滚其他已确认类型。
